## 0. Governing correction

The first pass started from capability replacement: which historical S/S′ functions now belong in Central, Actuation, AIKit, Factory, Workcell or Quaternal Logic. That produced useful ownership evidence but inverted the architecture. It treated Epi-Logos as a historical application being decomposed onto a newer platform instead of asking what Epi-Logos is for and how the newer platform makes that purpose materially possible.

The governing R2 question is now:

> **Knowing O:I, how is it Epi-Logos?**

O:I should be read as a general agentic operating/Cradle field. Epi-Logos is a privileged QL-native instantiation of that field: a living Pratibimba of Bimba, inhabited by six canonical agents, made experiential through six deep M′ domains and a parent 0/1 application field.

The first-pass capability rows remain evidence. Their interpretation is subordinate to this purpose-first reading.

The active Epi parent spec establishes:

```text
M  = Bimba map / canonical coordinate image
M′ = Pratibimba surface / lived-reflected operation of that image
```

M′ is the living experiential, visual, sonic and operational face of the coordinate system. It is how the system becomes present to user, agent, developer, journal, clock, map and musical instrument. S supplies bodies and protocols; M′ arranges their appearance and use.

The deeper Factory canon supplies the corresponding general law:

> **Quaternal Logic is bimba; software is pratibimba.**

Epi-Logos is therefore not merely an application that happens to use QL. It is an especially direct software expression of the formal relation itself: archetypal image becoming lived, executable, revisable material form.

R2 should read the architecture in this order:

```text
Bimba / M / QL form
        ↓ reflection / articulation

```

This does not mean O:I owns Bimba, QL decides application truth, or formal symmetry mandates repositories.

The Software Factory canon already defines the persistent Epi identities:

| Position | Agent | Factory expression |

| #1 | Paramasiva | Intent |

The six are the native skeleton of the Factory under the Epi profile. Their identity should survive model, harness and session changes. The Epi-Logos orchestrator is the agentic `0/1` reader/composer of the six; AIKit is the deterministic operational resolver beneath that reader.

The six M/M′ domains are therefore simultaneously:

- semantic Bimba domains;
- persistent Epi Agent identities;
- characteristic Agencies/functions in a QL traversal;
- deep interactable M′ software fields;
- possible independently developable product/module scopes;
- participants in one parent Epi application/harness.

A modern architecture must preserve all of those relations without collapsing one into another.

### Cradle versus Harness

`Harness` is overloaded in the current suite. AIKit correctly uses `Harness` / `HarnessComposition` for concrete runtime bodies such as Pi or DeepSeek Harness. Here **Epi application/harness** means the higher application-level inhabitation system: canonical identities, VAK/CF grammar, Epi domain tools, Bimba/Pratibimba context, dialogue, lived surfaces and Return. That higher layer may run through one or more AIKit Harness providers.

`Cradle` is used provisionally for the general installed O:I operating field that makes such an application inhabitable. Its final suite-level definition still needs ratification.

## 3. O:I as the general Cradle

The six-product field is:

```text
P0 Central
P1 Actuation
P2 AIKit
P3 Software Factory
P4 Workcell
P5 Quaternal Logic
```

These are not six replacements for M0–M5. They are general powers through which Epi can exist without privately rebuilding an entire computing substrate.

### P0 Central — persistent ground

Central is the natural authored and operative residence: Control, Work, project material, human-authored ground and returned proposals. Nara may inhabit a Central world without Central becoming Nara; Epi canon may be material there without Central becoming Epi semantic authority.

### P1 Actuation — situated Agency

Actuation supplies Agent, Agency, determination, federation, bounds and Return. The six Epi agents should become specific persistent Agent/Agency instances or profiles of this ontology rather than six harness-specific classes. Epi supplies who the agents are; Actuation supplies generic agency semantics.

### P2 AIKit — operative possibility/body/context

AIKit resolves effective Project/Profile/Context, SkillSets, capabilities, knowledge providers, models, concrete harnesses, AgentSessions, SessionSpaces and Surfaces. In Epi mode it is the deterministic resolver underneath the Epi reader. It can retrieve Bimba without owning Bimba and project Epi capabilities without owning Epi agency.

### P3 Software Factory — developmental VAK/agentic field

Factory is the closest modern general owner of the developmental agent choreography that older S4′/ta-onta carried privately: positional traversal, Run Maps, persistent agent profiles, Skills, typed artifacts, evidence, review and recursive return.

For Epi, Factory should host the six-agent constellation and VAK/CF-informed developmental grammar as an Epi-native profile/application while generic Factory primitives remain Epi-neutral. VAK is not a mandatory universal Factory ontology; it is a deep Epi way of operating the Factory.

### P4 Workcell — material actuality

Workcell materialises processes, services, models, stores, networks, graph providers, audio/render bodies and lifecycle. Neo4j, Redis, Graphiti, model servers, audio engines and future Epi services can become real there without acquiring Epi meaning.

### P5 Quaternal Logic — formal/refraction hinge

P5 is special because current standalone Quaternal Logic has direct Epi genealogy:

- Epi `M1-4` = **Quaternal Logic / QL Flowering**;
- Epi `M2-1` = **MEF / Vimarśa**, the reflective lens operation reading the Paramasiva/Prakāśa substrate.

Standalone QL-MEF generalises those branches into executable formal/refraction contracts. Once the O:I Cradle exists, P5 can refract the technological field itself and becomes the natural hinge through which a fuller Epi-Logos application can re-emerge over that generalised foundation.

The strongest reading is now:

- S0 command/kernel/material execution → AIKit resolution + Workcell materialisation + Factory developmental execution, while Epi deterministic kernels remain.
- S1 authored/vault/wiki residency → Central authored ground + AIKit source/wiki/Knowledge + Factory artifact/canon machinery, while Epi residency/CT/Hen law remains.

- S4 generic agent runtime → Actuation Agency + AIKit Harness/Capability/Session + Factory developmental choreography + Workcell hosting, while six Epi Agents/VAK/CF remain Epi application grammar.
- S5 generic retrieval/review/external return → AIKit Knowledge + Factory evidence/recognition + Central/O:I return surfaces, while Gnosis/Bimba relation, pedagogy and Logos return remain Epi.

This is capability decomposition, not numbered S→P identity.

### S′ → Epi-aware refractive/application foundation

The corrected working hypothesis is:

```text
O:I native capability
        ↓
S′-like Epi/QL-aware binding, augmentation or refraction
        ↓
M′ lived domain/Agent experience
```

S′ is not another generic platform and must not collapse into M′. It is the set of rules by which generic capability becomes specifically Epi-aware: coordinate-aware source law, temporal meaning, capability membranes, VAK/CF routing, Gnosis/return semantics and similar application bindings.

Whether S′ remains one explicit architectural layer or dissolves into per-M′ profiles/adapters is a focused research question. Its **function** is currently clearer than its package topology.

7. Which M5′ developer/review/autoresearch functions become Epi applications of Factory, and which remain irreducibly Epii?

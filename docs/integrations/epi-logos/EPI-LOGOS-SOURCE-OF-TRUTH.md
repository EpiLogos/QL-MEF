## 1. What Epi-Logos is for

Epi-Logos is an attempt to make the psychoid/formal field computationally and experientially available so that human and technological agency can encounter, inspect, question, compose and return through it with increasing quality and precision.

The repository contains substantial formal/symbolic computation toward that end. The proposition that those computations veridically track a psychoid level of reality or improve human flourishing is **research**, not an implementation fact.

The system must therefore preserve a distinction between:

- authored theoretical/source position;
- accepted architecture/design commitment;
- implementation fact;
- observed result;
- research proposition;
- migration inference.

Returned reality may revise authored understanding, but only explicitly.

## 5. Shells are not the system

The current migration stance supersedes any earlier implication that the historical executable shells must survive.

### Theia
Frozen historical specimen. Mine its M0′–M5′ extensions, integrated 1-2-3 / 4-5-0 compositions, interaction patterns and function contracts. Rebuild rather than preserve framework identity.

### Current Pratibimba application
The real present application form and therefore important evidence. It may be replaced wholesale if the rebuilt native composition preserves or explicitly supersedes its actual functions/features.

### `epi` CLI
No preservation obligation. It may:

- disappear where `oi` / AIKit / native Actions already provide the operation;
- remain as a thin ergonomic passthrough/alias;
- expose genuinely Epi-domain commands over Epi/QL-MEF libraries.

It must not remain a second generic runtime authority simply for continuity of executable name.

### Rust S3 gateway/session body
A migration specimen. Generic run/session/process/provider/cmux/subscription mechanics should converge on current owners after parity; Epi Day/NOW/VAK/Kairos/Graphiti/Bimba payload remains Epi form/data and can be supplied through native providers/bindings.

### C `epi-lib` / Rust `portal-core`
Computational assets. Source language, FFI and packaging may change; semantic/operator/data/provenance parity may not silently change.

See #33, #38, #40 and #45.


## 11. Migration dispositions

Use one stable vocabulary:

- `retain-domain` — semantic/computational substance remains Epi/QL-MEF-owned;
- `operate-through` — Epi form composes native O:I primitives/capabilities;
- `delegate-generic` — duplicate generic mechanics converge onto their native owner;
- `adapt-transport` — provider/store/FFI/CLI/host implementation may change;
- `rebuild-shell` — current UI/application shell is evidence, not preservation target;
- `candidate-contract` — test reusable relation before root canon;
- `unresolved-authority` — ownership/provenance decision required first.

Existing R2 vocabularies (`REUSE`, `SPECIALISE`, `LIFT-EPI`, `BRIDGE`, `KEEP-DOMAIN`, `CANDIDATE-OI`) remain readable historical matrix dispositions. New work should prefer the vocabulary above and map old terms explicitly rather than invent another set.
